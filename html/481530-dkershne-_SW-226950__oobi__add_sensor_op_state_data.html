[SW-226950] oobi: add sensor op state data

Need to persist sensor operational state that is set by PLDM commands
SetNumericSensorEnable and SetStateSensorEnables.  The oobi data
contains sensors that have been set to either DISABLED or UNAVAILABLE,
ENABLED sensors are not stored in the list, since all sensors by
default are enabled.

Note: We have a storage limit of 300 numeric sensors and 64 state
sensors due to space issues. If more than that is need to be set to
disabled or unavailble, the state will not be persisted across
resets.

oobi.h

  • Jason Smith (Line 104): nit: spell out 'num'
  • Jason Smith (Line 112): We could more tightly pack this data, allowing us to persist more sensors. For numeric sensors, we only need 1 bit to track 2 states - unavailable vs disabled. The sensor_ids max out at 1400; so we could use a single uint16, where the high bit indicates the op state, and the lower 15 are the sensor ID. Result: reducing from 3 to 2 bytes per sensor. For state sensors we need to track per-composite sensor, so likely also need an 'enabled' state; i.e. 2 bits per composite. A single uint16 with 8x 2-bit fields would work. Probably not worth shrinking the sensor_id in this context. Result: reducing from 10 bytes down to 4 bytes. If my math is right, this allows us to double the number of each type of sensor, still consuming the same 1KB of data.
  • Jason Smith (Line 129): 'disabled' is not quite right, since it also supports 'unavailable'; recommend renaming with 'op_state', example: struct hl_oobi_pldm_num_sensor_op_state numeric_op_state[OOBI_PLDM_MAX_NUM_NUMERIC_SENSORS]; struct hl_oobi_pldm_state_sensor_op_state state_op_state[OOBI_PLDM_MAX_NUM_STATE_SENSORS];
  • Michael Brooks (Line 105): this isn't really an "op state", given it's one bit. it's one specific value of the op state. presumably either `enabled` or `disabled`... not sure which without additional context or comments. i would have renamed it to match which value it represents. also, it would have made a sense to use the MSB for this, not the LSB. even if nothing else, it would have make hexdump debugging easier by aligning the multi-bit field. additionally, it would provide a path forward for expanding the op state bit by eating into sensor_id from the MSB (maybe not needed here, but just commenting as a best practice).
  • Michael Brooks (Line 105): i now understand this a bit more after reading downstream patches. it is effectively the LSB of the `oobi_sensor_op_state_t` enum, taking the values of DISABLED/0 or UNAVAILABLE/1. comments in the downstream patch about this. i would prefer to see the values of this field defined in this header so that the specification is more self-contained, and so that the conversion from this encoding to/from the enum is less implicit, but maybe there was rationale for defining this field as opaque.
